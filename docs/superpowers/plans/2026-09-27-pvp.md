# PvP Modes Implementation Plan (plan 4)

> **For agentic workers:** executed in parallel batches (worktrees), with one Opus review per batch. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Show research record `002-pvp-meta` in the app the way the Guild Conquest boss screen shows record 001. Each PvP mode, regular **Arena** (아레나) and **Rumble Arena** (와글와글 아레나), gets screens covering its rules, top teams with full builds, counters, usage and runes/gear, every claim cited.

**Architecture:** One database, with a `mode` dimension on content. Record 002 is curated into `research/002-pvp-meta/curated/*.json` and loaded by the same importer, extended with a manifest option for extra curated collections. New cited content types `counters` and `usage_stats`. The web app's `/arena/*` and `/rumble/*` routes (placeholders today) get real views that reuse the existing components.

**Spec:** `docs/superpowers/specs/2026-09-27-crumble-logbook-design.md`, extended by the user's 2026-09-27 direction: Guild Conquest is one part of a multi-mode app, and PvP research must be browsable like the boss screen.

## Global Constraints
- The data-core and web-app plans' constraints all apply: citations required, evidence never edited, importer all-or-nothing, layering, JSDoc, no narrative comments, Opus reviewers, explicit `git add`, `rtk proxy` for prettier/verify.
- `mode` enum: `guild_conquest | arena | rumble_arena`. Existing rows are `guild_conquest`.
- Names are stored in Korean as written. In PvP threads 바궁 = Wind Archer (바람궁수); record 001's glossary maps it to Princess Bari. The glossary needs a mode-aware or explicit fix (see D1).
- Counters are directed edges: "team A is beaten by team B, under conditions C, because of mechanism M", with a confidence level. Never present them as symmetric.
- Usage numbers carry their sample and capture time, and state when the game hides slots (crumb.gg's defense data is a lower bound).

## The curated format for record 002 (D1 writes it, D2 imports it)

`research/002-pvp-meta/curated/` holds the same collection files as record 001 (`manifest.json`, `sources.json`, `decks.json`, `runes.json`, `gear.json`, `mechanics.json`, `takeaways.json`, `timeline.json`, `glossary.json`, `meta.json`), with these additions:
- Every row in decks, runes, gear, mechanics and takeaways has `"mode": "arena" | "rumble_arena"`.
- Deck cookies may carry `"slot"`: the formation position as displayed, e.g. `"back-1"`… or `"row1-3"` (free text, documented in `meta.json`).
- `counters.json`: `[{ "id": "rye-vs-bari", "mode": "arena", "team": "<deck id>", "beaten_by": "<deck id>", "conditions": "…", "why": "…", "confidence": "high|medium|low", "sources": ["dc:…"] }]`
- `usage.json`: `[{ "mode": "rumble_arena", "kind": "cookie|core|pet|team", "subject": "<kr name or core label>", "members": ["<kr>", …] | null, "usage_pct": 97, "confirmed_pct": 70 | null, "sample": "top 100 defenses", "captured_at": "2026-09-27", "note": "lower bound: hidden slots", "sources": ["web:…"] }]`
- `meta.json` carries per-mode `lede`, `caveat` and a `rules` block (format, team size, battle length, seasons, rewards, season buffs), each with sources. `rules` becomes cited mechanics rows with a `topic: "rules"` marker.

## Step R: layering audit and extensibility refactor (first; D2/D3 build on it)

The user asked (2026-09-27) that the app be correctly layered and refactored for extensibility before PvP lands. The spec's success criterion 5 is the bar: *adding a new content type means a table, a schema, a route and a view, with no cross-cutting edits*. Adding a game mode should be data plus views, not new plumbing.

**R1 — Enforce the layering mechanically (tests, not convention):**
- An architecture test (a Vitest file scanning imports) fails when:
  - `routes/*` imports `repos/*` or `drizzle-orm`
  - `services/*` imports `drizzle-orm` query builders or `hono`
  - anything outside `repos/` and `db/` imports `drizzle-orm` (types excepted)
  - `apps/web/src` imports anything from `@crumble/server` except `import type`
  - `packages/schema` imports from `apps/*`
  - components import `src/api/*`, since components stay props-only
- Fix every violation it finds.

**R2 — Server: one registry for cited content types:**
- Today, adding a type means editing `repos/index.ts`, `services/index.ts`, `app.ts` (the route chain), `services/export.ts` (the snapshot tables, order and counts), the importer's clear order, and `CITED_ENTITY`.
- Introduce a single content-type registry: entity, table, repo factory, service factory, route path, list filters, snapshot position and FK order. Derive the repos, services, snapshot tables, restore order, counts and replace-clear order from it.
- `AppType` must keep full route types. If deriving the route chain from the registry loses Hono's inference, keep explicit `.route()` calls in one place, and add a test that every registered type is mounted and exported.
- Generic list filters (`mode`, `deck`, `boss`, `cookie`…) are declared per type in the registry and validated once, rather than a hand-written router per filter.
- The export service's hand-maintained table list and counts literal (flagged in the T9 review) go away.
- The glossary name-resolver key logic gets one exported `lookupKeys(entry)`, shared with the importer's collision warnings (flagged in the batch A review).

**R3 — Importer: split read/validate from write** (`import-record.ts` is ~485 lines and does two jobs). Collections are driven by the registry plus the manifest, so a new curated collection is a manifest entry and a mapper, not orchestration edits.

**R4 — Web: mode-driven views:**
- `src/app/modes.ts` becomes the single source for each mode's slug, label, record, sub-tabs and API filters.
- Views that exist for several modes (teams/decks, runes, gear, mechanics, takeaways, overview) take a `mode` prop and query with `?mode=`, instead of being copied per mode.
- Mode-specific screens (the conquest boss screen, PvP counters and usage) plug in through the mode config.
- The Guild Conquest routes keep their paths.

**R — gates:** behaviour unchanged. Every existing test passes unmodified, except tests that encoded a list now derived from the registry. `data/snapshot.json` is byte-identical after a fresh import. `rtk proxy pnpm verify` is green. The step has its own Opus review.

## Batch D (parallel)

### D1: Curate record 002 (research agent)
- Read all four lanes' `SYNTHESIS.md` and `08-extract/*.json`. Write `curated/*.json` in the format above: the top teams per mode as decks, with every cookie, level, star (or `"?"`), slot and why, pets and perks; counters; usage (from `03-sites` crumb.gg data); PvP rune and gear guidance; the rules as mechanics; takeaways per mode; timeline (Rumble Arena launch and seasons).
- Build `curated/sources.json` from the extractions (the same id conventions: `dc:<no>`, `nv:<id>`, `web:<slug>`).
- Write `research/002-pvp-meta/import.json`, with no rankings, and the capture rules for its `evidence/0{1,2,4}-*/dc|nv` folders.
- Resolve disagreements explicitly: Rumble's single 12-cookie meta (sites lane) vs the DC lane's "turtle vs charge" (hidden slots), and "Rye beats Bari" evidence that is actually Rumble. Put the resolution in takeaways and mechanics with confidence levels.
- Glossary: new PvP names, plus a note that 바궁 is ambiguous. Don't edit record 001's evidence.
- Validate: every cited id exists in `sources.json`, and every deck id referenced by counters exists.
- Also write the record's `README.md` (question, verdict per mode, reasoning with evidence pointers, sources, file index).

### D2: Server — mode, counters, usage, multi-record import (implementer)
- Schema: add `mode` (enum, notNull, default `guild_conquest`) to `decks`, `rune_builds`, `gear_recs`, `mechanics`, `takeaways`, `rng_factors`, `timeline`, `research_records`; add `slot` (text, nullable) to `deck_cookies`; add `topic` (text, nullable) to `mechanics`. New cited tables `counters` (`id` text PK, `mode`, `team_deck_id` → decks, `beaten_by_deck_id` → decks, `conditions`, `why`, `confidence`) and `usage_stats` (`id`, `mode`, `kind` enum, `subject`, `members` json, `usage_pct` real, `confirmed_pct` real|null, `sample`, `captured_at`, `note`). A new migration; don't regenerate the old ones.
- API: `?mode=` filter on every list endpoint that has the column; `/api/counters?mode=&deck=`; `/api/usage?mode=&kind=`; `/api/records` returns `mode`. The snapshot export/restore covers the new tables and columns, and the round trip covers every table.
- Importer: the seed schemas accept the optional `mode`, `slot`, `topic` fields (defaulting to `guild_conquest` for record 001); the manifest's optional `counters` and `usage` curated collections; **additive multi-record import**: importing record 002 into a DB that holds record 001 must not require `--replace`. Scope replace to a record: content rows get a `record_slug` column, so `--replace` clears only that record's rows. Record 001's re-import must stay byte-identical in the snapshot.
- Tests: mode filters, counters' deck refs (422 on unknown), usage ordering, importing 001 then 002 additively, replace scoped to one record, and snapshot round-trip equality.

### D3: Web — Arena and Rumble Arena views (after D2 merges; D1's data is only needed for the browser pass)
- Routes under `/arena/*` and `/rumble/*`: **overview** (rules card, takeaways, caveat, season buffs), **teams** (deck cards with formation slots, levels and why; reuse `Lineup`/`Kv`/`SourceChips`), **counters** (a matrix: rows = team, columns = beaten by, cells linking to the edge's why/conditions/sources, with confidence styling; plus a list view), **usage** (bar list per cookie/core/pet with sample and "lower bound" notes), **runes & gear** (the per-mode rune builds and gear recs, reusing the conquest runes/gear views filtered by `mode`).
- Guild Conquest views filter by `mode=guild_conquest`, so PvP rows don't leak into them.
- A **research** index page listing every record (slug, question, mode, status) and linking to its mode screens.
- Tests: each view with fixtures + empty state, the counter matrix orientation (never symmetric), and the mode filter wiring.
