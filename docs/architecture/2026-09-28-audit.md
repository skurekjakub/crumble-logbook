# Architecture audit: structure against the roadmap

Date: 2026-09-28 · Read against `87d0a9f` (main), re-checked against `6112b7e` after the fix lane merged; line references are to `6112b7e`. Read-only; nothing was changed.

**Roadmap this audit measures against** (from the user):

1. Simulators for every game mode, starting with the specced Guild Conquest encounter sim (`docs/superpowers/specs/2026-09-27-conquest-simulator-design.md`).
2. Scrapers and jobs triggered from the app (DC Inside, Naver, crumb.gg), and an easy path for new decks and new research records.
3. More game modes beyond Guild Conquest, Arena and Rumble Arena: stage pushing (story/world stages) and the Golden Drop encounter, each with views, backend logic and its own simulator.

Line counts below are `wc -l` at `6112b7e`. The fix lane's commits (`ce7923d`..`6112b7e`: deck-delete and counter-mode conflicts, the registry and importer layering rules, `ModeViewHeader`, JSDoc lint) are folded in; small defects in the files it touched are out of scope.

### 1.2 Extension points as they exist today

**A cited content type** (documented at `registry.ts:7-13`): a table in `packages/schema/src/tables/`, an `xInput`/`xPatch` pair in `inputs.ts` (12 lines of boilerplate each, e.g. `inputs.ts:47-57`), a `CITED_ENTITY` value (`enums.ts:77-91`), a registry `entry()` (`registry.ts:193-200`), one `.route()` line in `app.ts`, and a view. The generic repo (`repos/table-repo.ts`), service (`services/content.ts:219-247`), CRUD router (`routes/content.ts:61-98`), snapshot tables, restore order, import counts and replace-clear order (`importers/write-record.ts:19-36`) all derive from the registry. A table with a `mode` column gets `?mode=` for free (`registry.ts:170-200`). `registry.test.ts` also needs a hand-written seed (`SeededKey` `registry.test.ts:24-39`, `FILTER_CASES` `:58-79`).

**An aggregate** (deck, rune build): its own repo (`repos/decks.ts`, 216), service (`services/decks.ts`, 172), and a hand-registered slot in `Repos` (`repos/index.ts:30-40`) and `Services` (`services/index.ts:31-40`); the generic `crudRouter` still serves it (`app.ts:44-45`).

**A curated collection** in a record: an entry in `COLLECTIONS` (`collections.ts:328-541`) plus a file in the record's `curated/manifest.json`; `read-record.ts:45-55` and `write-record.ts` need no edits. `citedRows()` (`collections.ts:144-162`) covers the common case in ~5 lines.

**A non-collection capture** (rankings TSV, fight timeline, buff capture): a named optional block in `importManifest` (`manifest.ts:102-104`), a reader in `importers/{rankings,boss}.ts`, and a hard-wired step in `read-record.ts:127-141`.

**A game mode**: a `GAME_MODE` value (`enums.ts:47`), a `ModeSection` constant in `modes.ts` (tabs, scope, copy, mode-specific config), one route file per tab under `routes/<mode>/` (8 near-identical 7-line files per PvP mode, e.g. `routes/arena/teams.tsx`), the generated `routeTree.gen.ts` (630), and a research record covering it (`recordModes`, `tables/records.ts:23-34`). The PvP lane that added two modes touched 42 files in the web commit alone (`a1d00f1`, 42 files, +2758).

**A research record**: `research/NNN-slug/import.json` + `curated/manifest.json` + curated JSON, imported with `pnpm import:record` (`cli/import-record.ts`). Multi-record ownership (`recordSlug` on every owned table, `columns.ts:18-20`) and shared facts (sources, glossary, buff values: first loader owns, identical re-loads skipped, conflicts fail; `collections.ts:219-237`, `boss.ts:293-316`) already work.

### 1.3 What works well (keep)

- The registry is doing its job: repos, services, snapshot, restore, counts and clear order are all derived, and `registry.test.ts` catches an unmounted route or an unregistered entity. This is the pattern to extend, not replace.
- The read/validate-then-write split in the importer (`readRecord` → `WriteStep[]` → one transaction) is exactly what a job runner will need: a job can call `readRecord` asynchronously and hand the plan to a short synchronous transaction.
- `Store.transaction` being synchronous (`repos/index.ts:85-97`) is a deliberate correctness choice for `node:sqlite`; it constrains where async work (scrapers, sims) can live, and that constraint is healthy.
- The web's "views take a `ModeSection`, components are props-only, lib is pure" rule is enforced and holds; adding Arena and Rumble reused every shared view without copying it.
- Game facts already have a home distinct from research findings: `buff_values` (`tables/boss.ts:31-53`) has no `mode` and is shared by all records. The sim spec's `game.ts` tables (spec §7.2) follow the same shape.
- `data/snapshot.json` is a byte-level regression gate for every refactor below (the PvP plan already used it that way: plan 4, "Step R gates").

## 2. Friction against the roadmap

### 2.1 Simulators for every mode

**What the spec already gets right.** `packages/sim` as a pure package with `zod` as its only dependency (spec §7.1), game data passed in rather than read, the service as the only place that knows both shapes (§7.3), the architecture-test rules (§7.6). None of this needs changing.

**Where it bends when the second sim (Golden Drop, Arena, stage) arrives:**

1. *Package layout is conquest-shaped at the top level.* Spec §7.1 puts `kits/`, `scenario/` (luck draws, boss ramp, death schedule) and `params.ts` directly under `src/`. Kits, the boss scenario and the Piñata death schedule are conquest content; the clock, event queue, seeded RNG with named streams, `formulas/` (the bundle's `Gn`/`Ar`/`jr`/`Ne` are game-wide), Monte Carlo, common-random-numbers marginals and the provenance-tagged parameter type are kernel. If they are mixed at one level, the second engine either duplicates the kernel or reaches into conquest folders.
2. *The web hook is a nullable slot per feature.* `ModeSection` already carries `boss: BossConfig | null`, `leaderboard: … | null`, `rules: … | null` (`modes.ts:154-168`); §8.1 adds `sim: SimConfig | null`, with `SimConfig.boss` and `presetDecks` (Piñata-shaped). Each mode-specific screen adds a field every mode must set to `null`. Fine at 4 slots; a smell at 8.
3. *The route shape.* §7.4 mounts `/api/sim/{model,run,marginals,calibrate}` with `team, scenario` in the body. A second engine needs its own input schema; with one path the body becomes a discriminated union on `mode`, or the path gains a mode segment. Decide before S3 so `AppType` doesn't churn.
4. *Error mapping is a cross-cutting edit.* `app.ts:51-63` maps three error classes by `instanceof`; `SimInputError → 422` (§7.4) and any job error later each edit `app.ts`.
5. *Game facts owned by a research record.* §7.2 makes record 001 own `cookie_stats` etc. because the captures live there. `--replace` of 001 clears them (`write-record.ts:29-36`), which takes every mode's sim down until re-import, and a later mode's record has no natural place to add facts (a Golden Drop boss stat block is not "001's"). Shared-fact semantics (`insertBuffValues`, `boss.ts:293-316`) soften this but ownership is still per record.
6. *Seven new content types at once.* S1 adds 7 registry entries; each costs the 6-file checklist in §1.2 plus ~12 lines of `inputs.ts` boilerplate and a `registry.test.ts` seed. `inputs.ts` goes from 276 to ~360 lines of copy-paste.
7. *Reusable UI is trapped in the boss screen.* `FightTimeline` (150) is generic, but its helpers live in `lib/boss.ts` (313) next to the buff pivot, and `BossView.tsx` (547, the largest file in `apps/web/src`) holds `Survival`, `BuffTable`, `WhatToRun`, `AtkCheck` as internal functions (`BossView.tsx:299-547`). The sim page reuses `FightTimeline` with lanes (§8.2) and `AtkOrder`; a Golden Drop screen reuses the track math. Today that means importing from a conquest file.

### 2.2 Scrapers, jobs, adding decks and records

**State today.** The `jobs` table exists (`tables/jobs.ts`, `zod.ts:273-286`) and is deliberately unregistered (`registry.ts:210-211`, `export.ts:8-9`). There is no repo, service, route, runner, `jobs/` or `scrapers/` directory, although the design spec lists both layers and the job contract (`crumble-logbook-design.md`, "Server" table and "Jobs"). The actual scrapers are 9 Python scripts inside evidence folders (`research/001-guild-conquest-meta/evidence/{dc_scrape,nv_scrape,digest,build_sources}.py`, `14-global/*.py`), run by hand; 2,227 evidence files were captured that way. Success criterion 3 of the design spec ("a scrape can be triggered from the UI and its captures land in a record") is unmet.

**Where the layering needs a decision, not a rewrite:**

1. *Async work versus synchronous transactions.* `Store.transaction` rejects async callbacks at compile time (`repos/index.ts:85-97`). A job's `run` is async (network, agent-browser). The fit is: the job does its I/O, writes captures under `research/<slug>/evidence/`, then calls `readRecord` and `writeRecord` (both sync) at the end. The runner must never hold a transaction open across an `await`. This is a rule to write into `architecture.test.ts`, not a limitation to remove.
2. *Which layer owns jobs.* Routes may import only services (`architecture.test.ts:101-109`). So `routes/jobs.ts` needs a `services/jobs.ts` façade over a runner that lives beside services (it uses `Store`, importers and scrapers). Scrapers should be pure I/O adapters (URL → typed capture + file path) with no repo access, so they are testable against fixtures as the spec asks.
3. *The source-site enum is closed.* `SOURCE_SITE = dc | nv | web` (`enums.ts:5`, whose comment wrongly says `dc` is a Discord; it is DCInside). crumb.gg and YouTube captures are `web:` ids today; a crumb.gg scraper wanting its own capture layout gets no site of its own without an enum change. Acceptable, but say so in the job design.
4. *Capture layout is per record and per site.* `import.json` `captures[]` (`manifest.ts:95-101`) maps `{site, dir, file}` per record; a scraper writing into a record must append a capture rule or write into an existing dir. Cheap to handle: the job appends to `import.json` through the same schema.
5. *Adding a deck through the API already works* (`POST /api/decks`, `services/decks.ts:133-148`) but rows written that way have `recordSlug: null` (`columns.ts:14-16`) and are invisible to `--replace`, and the snapshot is the only place they persist. Adding a deck "properly" means editing `research/<slug>/curated/decks.json` and re-importing. There is no scaffold for a new record (`import.json`, `curated/manifest.json`, README skeleton per `.claude/skills/deep-research/SKILL.md`); each has been hand-written.
6. *The curated `mode` default.* Every curated row schema defaults `mode` to `guild_conquest` (`seed/schema.ts:26`), as does the DB column (`columns.ts:9`) and the record itself (`seed/map.ts:256`). Record 001's rows omit `mode` and rely on this. A new stage-mode record whose author forgets `mode` on a row files it under Guild Conquest silently. The default made sense with one mode; it is now a trap.

### 2.3 New game modes (stage pushing, Golden Drop)

**Adding a mode today** (measured against the PvP addition, commits `053f8d3`, `f5c378b`, `a1d00f1`):

That is ~12 files, none of them plumbing; the registry and services need nothing. Good. The friction is in what the mode *means*:

1. *Conquest concepts on generic tables.* `decks.atkOrder`/`atkOrderNote` (`tables/decks.ts:18-19`) exist for Pomegranate beam targeting; PvP decks use `formation` and `deck_cookies.slot` instead. `scores` (`tables/scores.ts`) is `damageG`/`powerG` with no `mode` column at all; `scoresQuery` admits "Scores carry no mode, so the scope only keys the cache" (`queries.ts:114-116`), and `ScoresView` is simply not mounted for PvP. A stage mode's result is "cleared / not, with which team, in how many attempts"; Golden Drop's is damage again. `rankings.board` is `players | guilds | power` (`enums.ts:39`), crumb.gg's conquest boards; Rumble's live board was filed as `usage_stats` instead. `GEAR_CONTEXT = raid | arena | stage` (`enums.ts:35`) is a second, parallel mode-ish enum keyed to the in-game preset; Golden Drop has no value.
2. *The boss screen is Piñata-and-Cherry-shaped.* `BossConfig` is parameterised by `id` and topics (`modes.ts:99-136`), which is right, but `deck`, `catcherKr`, `atkPetKr`, `hasteKr`, `debufferKr` (`modes.ts:122-132`) describe one deck's ATK-order mechanics, and `BossView`'s "What to run" and "ATK-order check" sections (`BossView.tsx:441-547`) assume them. A Golden Drop encounter screen needs the timeline and survival sections and probably not those two.
3. *Per-mode config and copy in one file.* `modes.ts` carries three modes' copy, `PVP_COPY`, the full `BossConfig`, `LeaderboardConfig`, `RulesConfig`, nav helpers and shared sections. Two more modes plus `SimConfig` blocks put it past 700 lines.
4. *Record ↔ mode is two relations.* `research_records.mode` ("filed under") and `record_modes` ("covers") are merged by `recordsCovering` (`services/records.ts:40-48`) and by `ResearchView.coveredModes` (`ResearchView.tsx:19-22`). Workable; a record that covers stage pushing and Golden Drop will exercise it.
5. *Per-mode CSS is global.* `boss.css` (172) and `pvp.css` (263) are imported in `main.tsx:10-11`. Fine at two; class-name collisions become likely at five.

### 2.5 Gaps in the enforced rules

`architecture.test.ts` covers `apps/server/src`, `apps/web/src`, `packages/schema/src` (`ROOTS`, `:32`). Since `9ec38a1` it pins `registry.ts` to schema, zod and drizzle types (`:123-132`) and forbids `importers/` from importing routes or hono (`:133-137`). That importer rule is a deny-list, not an allow-list: importers may still import anything else (today they import `repos/*` types, `services/names` at `collections.ts:17`, and `services/deck-modes.ts`, and call repos through `WriteStep`). Nothing covers `cli/` (composition roots) or the future `jobs/`, `scrapers/`, `packages/sim`. The sim spec §7.6 adds the `packages/sim` rules; jobs and scrapers need theirs written at the same time, or the first job will import whatever is convenient.

## 3. Recommended restructuring, in order

Legend: **S** < half a day, **M** one to two days, **L** several days. "Now" means before the sim's S1 lands, because S1 multiplies the cost of the thing it fixes.

### Do now: cheap, and every roadmap item benefits

**R1. Split `apps/web/src/app/modes.ts` by mode.** `app/modes/{types.ts, conquest.ts, arena.ts, rumble.ts, shared.ts, index.ts}`; `index.ts` re-exports `MODES`, `SECTIONS`, `sectionForPath`, `activeTab`, `topicsShownElsewhere`. `PVP_COPY` goes to `arena.ts`/`rumble.ts` via a small `pvp-shared.ts`. No behaviour change; every import of `../app/modes` keeps working through `index.ts`.
Why: roadmap 1 (the `sim` block lands in `conquest.ts`, not a 550-line file) and 3 (a new mode is a new file). Files: `modes.ts` → 6 files; tests unchanged. **S**, risk nil.

**R2. Split the boss screen into reusable parts.** `components/encounter/{Survival,BuffTable,WhatToRun,AtkCheck}.tsx` from `BossView.tsx:299-547`; `lib/boss.ts` → `lib/fight-track.ts` (`trackPercent`, `secondsLeft`, `whenLabel`, `staggerRows`, `markerRows`, `survivalTitle`, `eventLabel`) and `lib/buffs.ts` (`pivotBuffs`, `buffStars`, `starCells`, effect names). `FightTimeline.tsx:3` imports `lib/fight-track`.
Why: roadmap 1 (sim page needs `FightTimeline` lanes and `AtkOrder` without importing a boss file) and 3 (Golden Drop screen reuses the track and survival cards). Files: 2 → ~8; `boss-view.test.tsx` and `boss-lib.test.ts` split accordingly. **S/M**, risk low (pure moves; `data/snapshot.json` untouched; view tests are the gate).

**R3. Make manifest "extra" blocks pluggable, like collections.** Today `fightEvents`, `buffValues` and `rankings` are named fields of `importManifest` (`manifest.ts:102-104`) with hard-wired steps in `read-record.ts:127-141`. Introduce `importers/extras.ts` with an `EXTRAS` map `{ rankings, fightEvents, buffValues, gameData }`, each `{ schema: ZodType, read(recordDir, spec, ctx): WriteStep[] }`; compose `importManifest` from `COLLECTIONS`-style keys as `curatedManifest` already does (`collections.ts:543-552`); `readRecord` iterates. Split `boss.ts` into `importers/fight-events.ts`, `importers/buff-values.ts` and `importers/shared-facts.ts` (the generalised `insertBuffValues`, which spec §7.2 asks for anyway: "the shared-fact step generalises `insertBuffValues`").
Why: roadmap 1 (S1's `gameData` block becomes one entry, not edits to `manifest.ts` + `read-record.ts`), 2 (a scraper's capture type is one entry), 3 (stage or Golden Drop captures likewise). Files: `manifest.ts`, `read-record.ts`, `boss.ts` → 4 files, plus `manifest.test.ts`. **M**, risk low-medium: the manifest schema must stay `strictObject` and reject unknown keys exactly as now; `import-record.test.ts` (690 lines) is the gate and the snapshot must stay byte-identical.

**R4. Drop the row-level `guild_conquest` default in curated schemas.** Make `mode` optional in `seed/schema.ts:26` and resolve it in `seed/map.ts` from `manifest.record.mode` (`manifest.ts:91`), failing the import with the file and row when neither states it. Record 001's `import.json` gains `"mode": "guild_conquest"` (one line); no curated row changes. Keep the DB column default (`columns.ts:9`) for now: removing it is a migration and only matters for raw API writes.
Why: roadmap 3 (a new mode's record cannot silently file rows under conquest). Files: `seed/schema.ts`, `seed/map.ts`, `research/001-*/import.json`, seed tests. **S**, risk low. Coordinate with the fix lane, which is editing curated data.

**R5. Collapse the `inputs.ts` boilerplate before S1 adds seven types.** A `citedInputs(insertSchema, { omit })` helper returning `{ input, patch }` (the pattern at `inputs.ts:47-57` repeated 11 times); keep the named exports so the registry is unchanged.
Why: roadmap 1 (S1). Files: `inputs.ts`, `inputs.test.ts`. **S**, risk nil.

**R6. Table-driven error mapping.** `errors.ts` exports `httpStatus(err): {status, body} | undefined`; `app.ts:51-63` becomes one line. Sim (`SimInputError`) and jobs (`JobRejected`, `JobNotRunning`) then never touch `app.ts`.
Why: roadmap 1 and 2. Files: `errors.ts`, `app.ts`, `app.smoke.test.ts`. **S**, risk nil.

**R7. Write the missing layering rules now, in `architecture.test.ts`,** so the next additions land inside them: turn the importer deny-list (`:133-137`) into an allow-list (`repos` types and `Store`, `registry`, `errors`, `services/names`, `services/deck-modes`); `cli/` is a composition root and may import anything below routes; `packages/sim` is pure (spec §7.6 verbatim); `scrapers/` import no `repos`, `services`, `db` or `drizzle-orm`; `jobs/` import no `routes` or `hono`; only `services/jobs.ts` imports `jobs/`. Add `packages/sim/src`, and later `apps/server/src/{jobs,scrapers}`, to `ROOTS`.
Why: all three items. File: `architecture.test.ts` (the fix lane's rules have merged, so this is additive). **S**, risk nil.

**R8. Split `collections.ts`.** Move `writeShared`, `differences`, `SOURCE_FIELDS`, `GLOSSARY_FIELDS`, `crossRecordGlossaryWarnings`, `assertUnclaimed`, `glossaryWarnings` (`collections.ts:170-316`) to `importers/shared.ts`; `COLLECTIONS` stays. Consider co-locating each collection's `seedX` schema, `mapX` mapper and `COLLECTIONS` entry in `importers/collections/<name>.ts` so a new collection is one file rather than edits to `seed/schema.ts`, `seed/map.ts` and `collections.ts`.
Why: roadmap 2 and 3 (new curated collections per mode: stages, encounter facts). **S** for the split, **M** for the co-location; risk low, gate is `import-record.test.ts` + snapshot. The co-location can wait for the first new collection.

### Do at the sim's S2/S3, at no extra cost

**R9. Lay `packages/sim` out as kernel + modes from the first commit.**

```
packages/sim/src/
  index.ts                 runSim, runMarginals, calibrate, MODEL_VERSION
  input.ts                 shared input pieces; re-exports each mode's input schema
  kernel/  rng.ts, clock.ts, queue.ts, stacks.ts, deaths.ts, params.ts (Provenance type)
  formulas/ stat.ts, damage.ts, buff.ts, haste.ts, debuff.ts        (game-wide, from the bundle)
  analysis/ montecarlo.ts, marginals.ts, sensitivity.ts, calibrate.ts
  data.ts                  GameData (game facts; mode-neutral)
  modes/conquest/  input.ts, scenario/ (luck, boss ramp, death schedule), kits/, engine.ts, params.ts
```
Nothing else from spec §7.1 changes. Do **not** write a `SimMode` interface until the second engine exists; the folder boundary is enough, and `architecture.test.ts` can forbid `kernel/`, `formulas/`, `analysis/` from importing `modes/`. **S** (naming only), risk nil.

**R10. Put the mode in the sim route path: `/api/sim/:mode/{model,run,marginals,calibrate}`**, validated against the modes the sim package exports, with each mode's body schema chosen by the param. Hono's typed client handles path params, so `AppType` is stable when Golden Drop arrives. Alternative: `mode` as a discriminator in the body; either is fine, pick one before S3. **S**, risk nil.

**R11. Own game facts outside research records.** Allow `recordSlug: null` on game-fact tables to mean "loaded from a capture, owned by no record", or give them a fixed pseudo-owner such as `game-data`. Then `--replace` of 001 does not clear the sim's inputs, and a Golden Drop record can add facts without owning the cookie catalog. Needs a decision (§5, Q2). **S/M** once decided; touches `write-record.ts:19-36` (`OWNED_KEYS`), `shared-facts.ts`, and the import tests.

**R12. `SimConfig` on the mode: keep it a nullable slot for now**, in `app/modes/conquest.ts` after R1. Revisit the "one nullable field per mode-specific screen" pattern when a mode has more than three such screens (a `screens: ReadonlyArray<ModeScreen>` discriminated union is the likely shape), not before.

### Do when the roadmap item starts

**R13. Jobs and scrapers (roadmap 2).** Follow the design spec's contract; place it as:

```
apps/server/src/
  scrapers/   dc.ts, naver.ts, crumbgg.ts        pure I/O: fetch → typed capture; write under research/<slug>/evidence/
  jobs/       runner.ts (concurrency 1, persisted in `jobs`, orphan `running` → `failed` on boot)
              kinds/{scrape-dc,scrape-naver,scrape-crumbgg,import-record}.ts   { kind, params: zod, run(ctx) }
  repos/jobs.ts            CRUD over `jobs` (stays unregistered: transient)
  services/jobs.ts         enqueue/list/get/cancel façade the route uses
  routes/jobs.ts           POST /jobs, GET /jobs, GET /jobs/:id, POST /jobs/:id/cancel
```
Rules: a `run` never holds a `Store.transaction` across an `await`; captures are files first, then `readRecord`/`writeRecord` at the end (one sync transaction); `import.json` capture rules are appended through `importManifest`. The web gets a shared `Jobs` section (`SHARED_SECTIONS`, `modes.ts:389-426`) with a log view. Include a `scaffold:record` kind (or CLI) that writes `import.json`, `curated/manifest.json` and the README/STATE skeletons from the deep-research contract, so "add a record" is one command. Port the Python scrapers to TS as the spec says, or shell out to them from a job kind as a first step; the runner and API shape are the same either way. **L**, risk medium (network, rate limits, agent-browser lifetime on Windows ARM64).

**R14. Result and ranking tables per mode (roadmap 3, stage mode).** When the stage mode's record exists, decide between adding `mode` to `scores` and generalising `damageG` to a `value` with a per-mode unit, or introducing `stage_clears` as its own content type. The registry makes the second cheap and keeps 배 conquest-only, which matches the "배 is only a normaliser" rule; lean that way. Same question for `rankings.board`. **M**, risk low. Not before the mode exists.

**R15. `BossConfig` → `EncounterConfig` with optional sections (roadmap 3, Golden Drop).** Make `whatToRun` and `atkCheck` optional blocks (`{ deck, gearContext }` and `{ catcherKr, atkPetKr, hasteKr, debufferKr }`), keep `facts`, `survival`, `fightSeconds`, `lengthEvent`, `id`. After R2 this is config plumbing only. **S/M**. Not before the second encounter.

**R16. `routes/$mode/` instead of one folder per mode (roadmap 3, at the fourth mode).** Today 3 modes × 8 tabs = 24 seven-line files. At five modes that is ~45. TanStack's dynamic segment with `beforeLoad` validating `params.mode` against `MODES` (else `notFound()`) collapses them to one folder; `AppPath` (`modes.ts:18`) becomes `{ to, params }`. Cost is typed-link churn across views and tests, so do it once, when the count justifies it, not now. **M**, risk medium.

**R17. Generalise `refs` beyond decks** (`registry.ts:144`, `content.ts:231-243` hard-code `repos.decks.exists` and the deck-mode check) the first time a content type references another aggregate (a `stages` table, an `encounters` table). **S** at that point.

### Deliberately not recommended

- A generic "mode plugin" abstraction on the server. Modes are a column value; the registry, services and routes are already mode-agnostic. Keep it that way.
- Deriving `app.ts`'s `.route()` chain from the registry. Plan 4 R2 already weighed this: the explicit chain is what keeps `AppType` fully typed, and `registry.test.ts:262` catches omissions.
- Splitting `packages/schema` per mode. Tables are shared; the mode is data.
- Moving per-mode CSS into components now. Two files; revisit with the third mode's stylesheet.

## 5. Risks and open questions for the user

**Risks**

- Whoever lands R1–R8 should start from a clean tree, each step behind the byte-identical snapshot gate.
- R3 changes how `import.json` is validated; the `strictObject` contract (unknown keys fail) must survive, or a typo in a future record imports silently.
- R11 (ownerless game facts) changes `--replace` semantics; document it in the README's multi-record gotchas.
- R16 (dynamic mode routes) touches every typed link; it is the one refactor with real churn, which is why it is deferred to the fourth mode.
- The sync `Store.transaction` means a long job can never wrap its whole run in one transaction; a crash mid-scrape leaves files but no rows, which is the right failure mode, but the job log must say so.

**Open questions**

1. **Mode routing.** Keep one route folder per mode (typed static links, 8 files per mode) or move to `routes/$mode/` when the stage mode arrives (R16)? The answer sets the "add a mode" checklist's step 4.
2. **Who owns game facts?** Record 001 (as the sim spec says), a dedicated `game-data` pseudo-record, or ownerless rows (R11)? This decides what `--replace 001` clears.
3. **Sim API shape.** `/api/sim/:mode/run` (R10) or one `/api/sim/run` with `mode` in the body?
4. **Results for non-damage modes.** Extend `scores` with `mode` and a unit, or add per-mode result tables (`stage_clears`) and keep `scores` conquest-only (R14)? The latter keeps 배 out of modes where it means nothing.
5. **Scrapers: port or wrap?** The design spec says port the Python scrapers to TypeScript. A first job kind that shells out to the existing scripts would ship the job runner and UI sooner; is that acceptable as a step, or must the runner wait for the port?
6. **What is "stage pushing" as data?** Per-stage teams (a `stages` dimension and clear records) or one general PvE team with notes? This decides whether R14 and a `stages` content type are needed at all.
7. **Golden Drop's shape.** Is it a timed encounter with a fight timeline like the Piñata (fits `fight_events` and `EncounterConfig`, R15), or a different loop that needs its own tables?
8. **A mechanical file-size rule?** The user's rule is "no single huge files"; `architecture.test.ts` could fail any source file over N lines (300–350 would flag the six files in §2.4). Do you want that enforced, and at what N?
9. **Source sites.** Should crumb.gg and YouTube captures get their own `SOURCE_SITE` values when scrapers exist, or stay `web:`?
