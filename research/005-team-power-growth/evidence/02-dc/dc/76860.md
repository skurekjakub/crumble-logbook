# [일반] 반죽 까는 양 왜 안올리냐?(분석글)

## Body

클뜯 결과 클라에서 서버로 보내는 뽑기 요청에는 사용할 장비 프리셋, 한 번에 뽑을 개수, 자동판매 필터 사용 여부가 들어감.
그래서 한 번에 뽑는 양을 늘리는 게 무조건 서버에 손해가 아님.
예를 들어 반죽 500개를 소모할 때 50개씩 뽑으면 요청이 10번인데, 500개씩 뽑으면 1번이면 됨. 요청마다 반복되는 확인이나 통신 비용을 줄일 수 있어서, 잘 만들면 더 효율적일 수도 있음.
다만 기존과 같은 간격으로 한 번에 10배씩 뽑게 하면, 같은 시간에 처리해야 하는 장비 수도 늘어남. 여러 사람이 동시에 대량으로 소모하면 순간적으로 서버 부담이 커질 가능성은 있음. 그렇다고 서버 전체 부하가 정확히 10배가 되는건 아님.
전에 다른 사람한테 장비를 하나하나 따로 계산한다는 이야기는 들었는데, 개발사에 확인한 것도 아니고 서버 코드를 본 것도 아니라 실제 구현은 모름. 아래는 확률이 고정된 독립시행이라고 가정한 이야기임.
이 조건이라면 이항분포나 다항분포를 이용해서 당첨 개수나 등급별 개수를 묶어서 추첨하는 방법도 있음.
쉽게 말하면 500개를 하나씩 뽑고 등급별로 세는 대신, 처음부터 “500개 중 각 등급이 몇 개 나올지”를 원래와 같은 확률로 정하는 방식이 있음.
이걸 제대로 구현하면 하나도 못 먹을 확률부터 여러 개 먹을 확률까지 유지할 수 있음.
근데 이걸 쓴다고 장비 500개에 필요한 모든 작업이 계산 한 번으로 끝나는게 아니라서 장비별 옵션을 정하고, 자동판매 여부를 판단하고, 보상을 계산하고, 결과를 저장하는 작업은 남을 수 있음.
예를 들어 특정 등급은 옵션과 관계없이 전부 판매하고 판매 보상도 같다면, 개수만큼 보상을 합산하는 식의 최적화를 검토할 수 있음. 반대로 옵션을 보고 보관 여부를 정한다면 그 조건까지 반영해야 함. 보관함이 차서 멈추는 규칙 같은 것도 유지해야 하고.
실제로 무슨 코드를 쓰는지는 몰라서 단정 지을수는 없긴 함... 이미 비슷한 방식을 쓰고 있을 수도 있고, 실제로 시간이 많이 걸리는 부분이 추첨이 아니라 옵션이나 저장 쪽일 수도 있음.
내 생각은 한 번에 뽑는 양을 늘리면 이용자도 편해지고, 서버도 요청마다 반복하는 일을 줄일 여지가 있으니 개선을 해주면 좋겠는데 ...
세 줄 요약
1. 한 번에 뽑는 양을 늘리면 같은 반죽을 소모하는 데 필요한 요청 횟수를 줄일 수 있음.
2. 반대로 같은 시간에 더 많은 장비를 처리하게 되면 순간적인 서버 부담은 커질 수 있음.
3. 확률을 유지하면서 묶어 처리하는 방법은 있지만, 실제 개선 효과와 현재 제한의 이유는 서버 구현을 몰라서 단정할 수 없음.
물론 사람들이 게임 접어서 서버 부하 줄어든다는 나쁜 말은 ㄴㄴ.
